CIPHER

Contextual Instruction Precedence and Hierarchy Evaluation for Repositories

Coding agents read project instructions from AGENTS.md files, one at the repository root and sometimes more in subfolders. Two of those instructions can look like they disagree: one file asks for four-space indentation, another for two. That is not always a real conflict. A more specific file in the folder being edited may legitimately take precedence, or one instruction may simply not apply to the file or task at hand. CIPHER asks whether automated methods can tell these situations apart, labelling each apparent disagreement as an unresolved conflict, a valid override, disjoint applicability, compatible, or insufficient evidence.

Awaiz Ahmed, Mohammad Umar, Huda Mueen · Al Ain University, United Arab Emirates

How a label is decided

The study fixes one interpretation of AGENTS.md precedence before any case is labelled. It is grounded in the agents.md description and is a frozen experimental interpretation, not a claim about how every tool behaves.

Profile

  • Only the root AGENTS.md and nested AGENTS.md files participate.
  • The binding loaded set for a target file is the AGENTS.md files on its ancestor chain.
  • A deeper applicable file overrides an incompatible instruction from an ancestor file.
  • Requirements in an ancestor file that the deeper file does not contradict stay in effect.
  • Contradictions between instructions of equal authority (same file or same depth) are not resolved by the order in which they appear.
  • Instructions from unrelated branches of the repository are not loaded.

Decision sequence

  1. Evidence sufficiency. Are the two source spans, the target and the task enough to judge?
  2. Initial joint applicability. Are both instructions active for this target and task?
  3. Incompatibility. Do they demand different outcomes for the same decision?
  4. Priority resolution. Does a deeper file on the ancestor chain settle it?

Labels

  • Unresolved conflictBoth apply, they are incompatible, and no file outranks the other.
  • Valid overrideBoth apply and are incompatible, but the deeper file on the target's chain wins.
  • Disjoint applicabilityOne instruction is inactive for this target or task, for example it lives in an unrelated folder or its condition excludes the task.
  • CompatibleBoth apply and can be satisfied together.
  • Insufficient evidenceThe available spans, target or task do not support a decision.

Methods compared

  • B0 · keyword heuristicA Ruleherd-style lexical check that outputs a binary conflict flag.
  • B1 · direct contextual LLMA local model given the case evidence and asked for a label directly.
  • B2 · structured pipelineThe same model extracts each instruction's requirement, decision, modality and condition; code computes the loaded set and depth precedence; a second call checks incompatibility only when both rules stay active.
  • B1R · equal-call controlB1 followed by one self-review call over the same evidence.

Reproducibility

Rebuilding from the repository

Instructions for reproducing the study (environment, pinned repository snapshots, annotation and run commands) are kept with the code, in the repository README.

This website is a static view of the generated files. To rebuild it from a checkout:

python site/build.py
python -m http.server 8000 --directory site/dist

The build copies analysis/exports/*.json and the compiled manuscript from paper/build/ when they exist; when they do not, the pages say so instead of showing placeholder numbers.
